# Business Rules Used

The Gold implementation uses:

```text
quality_check_result = 'PASS'
```

to determine eligible Silver records.

Revenue calculations include only:

```text
order_status = 'Completed'
```

orders.

`lifetime_value_actual` is calculated from the actual revenue generated by qualifying completed orders.

Customers with no qualifying orders are retained so they can later be classified as:

```text
Inactive
```

# 1. Sales by Product

Created:

```text
ecommerce_sales.gold.sales_by_product
```

The implementation:

* starts from valid Silver products,
* joins qualifying completed orders,
* preserves valid products even if they have no completed orders,
* calculates:

```text
product_id
product_name
category
total_orders
total_revenue
avg_order_value
```

Order counts use:

```text
COUNT(DISTINCT order_id)
```

Revenue fields are cast to:

```text
DECIMAL(20, 2)
```

### Why accepted

This matches the approved Gold grain:

```text
one row per product_id
```

and produces the required product-level commercial metrics.

---

# 2. Revenue by Customer

Created:

```text
ecommerce_sales.gold.revenue_by_customer
```

The implementation:

* starts from valid Silver customers,
* aggregates qualifying completed orders,
* LEFT JOINs revenue back to customers,
* retains customers with no qualifying orders.

Required measures include:

```text
total_orders
total_revenue
avg_order_value
lifetime_value_actual
```

The implementation defines:

```text
lifetime_value_actual = total qualifying completed-order revenue
```

Customers with no qualifying revenue receive zero values.

### Why accepted

This provides a customer-level analytical table while preserving customers required for the Inactive segmentation category.

---

# 3. Daily and Weekly Trends

Created:

```text
ecommerce_sales.gold.daily_weekly_trends
```

This output was originally treated as an optional enhancement during planning, but the project scope was updated so it is now implemented as a normal Gold deliverable.

The table contains both:

```text
DAILY
WEEKLY
```

period types.

Required columns are:

```text
period_type
period_start
total_orders
total_revenue
avg_order_value
```

Daily periods use:

```text
order_date
```

Weekly periods use:

```text
DATE_TRUNC('WEEK', order_date)
```

Both use the same qualifying completed-order population.

### Why accepted

One table can support both daily and weekly trend analysis without creating two separate models.

The grain is:

```text
one row per period_type + period_start
```

---

# 4. Customer Segmentation

Created:

```text
ecommerce_sales.gold.customer_segmentation
```

Customers are ranked by:

```text
lifetime_value_actual DESC
```

using:

```text
NTILE(5)
```

to identify the top 20% revenue group.

The segmentation precedence is:

```text
High-Value
→ top revenue quintile with at least one qualifying order

Repeat
→ more than one qualifying order

One-Time
→ exactly one qualifying order

Inactive
→ zero qualifying orders
```

The final output contains:

```text
segment_type
customer_count
avg_revenue
total_revenue
```

The SQL explicitly preserves all four expected segment labels even when a segment contains zero customers.

### Why accepted

This makes the segmentation deterministic and data-driven rather than relying on an arbitrary fixed revenue threshold.

# What I Accepted

## 1. Separate SQL Files for Gold Models

Each Gold dataset is defined independently in SQL.

### Why accepted

The transformations are aggregation-heavy and naturally expressed in SQL.

It also keeps each business model easy to inspect.

---

## 2. Python as the Gold Orchestrator

Python is used only to:

* execute SQL files,
* create the schema,
* validate output,
* coordinate dependencies.

### Why accepted

This provides a clear split:

```text
SQL
= business transformation

Python
= orchestration and validation
```

---

## 3. Completed Orders as Revenue

Only:

```text
order_status = 'Completed'
```

contributes to Gold revenue.

### Why accepted

This gives the project a clear and explainable revenue definition.

---

## 4. PASS Silver Records for Gold

Gold uses:

```text
quality_check_result = 'PASS'
```

records.

### Why accepted

This provides a simple, conservative rule for consuming validated Silver data.

---

## 5. Top 20% High-Value Rule

Cursor uses:

```text
NTILE(5)
```

and assigns the first quintile to High-Value customers.

### Why accepted

This avoids inventing an arbitrary revenue amount and makes the threshold adapt to the generated dataset.

---

## 6. Inactive Customer Preservation

The customer revenue model starts with valid customers and LEFT JOINs revenue.

### Why accepted

Without this approach, customers with zero qualifying orders would disappear and could never be classified as Inactive.

---

## 7. Daily and Weekly Trends Added to Core Gold Scope

### Why accepted

The implementation is small, useful, and fits naturally into the Gold analytical layer.
