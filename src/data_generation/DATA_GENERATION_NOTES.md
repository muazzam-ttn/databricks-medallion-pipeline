# Synthetic Data Generation Notes

## Scope and outputs

`generate_sample_data.py` implements Checkpoint 2 only. It creates:

- `data/customers.csv` — 10,000 physical rows
- `data/orders.csv` — 100,000 physical rows
- `data/products.csv` — 500 physical rows

The generator uses Python, pandas, and Faker. All names, email addresses, and
other customer-like values are generated by Faker; no real customer data is
used.

## Reproducibility

Generation is deterministic:

- Python random seed: `20260820`
- Faker instance seed: `20260821`
- Faker locale: `en_US`
- Fixed generated-data date range: `2020-01-01` through `2025-12-31`

The generator uses its own `random.Random` and Faker instances so execution
does not depend on random state from importing code.

## Generation approach

Data is generated in dependency order:

1. Products
2. Customers
3. Orders

Each dataset starts as a valid baseline. Baseline assertions check key
uniqueness, parent references, required values, approved domains, positive or
non-negative business values, and amount consistency. Intentional defects are
injected only after those checks pass.

Product names combine synthetic category-specific terms and a generated
identifier. Product prices and costs are created from integer cents and stored
with two decimal places. Customer names, emails, countries, and signup dates
come from Faker. Orders initially reference existing customer and product IDs;
their `unit_price` comes from the referenced product, and `total_amount` is
calculated as `quantity * unit_price` using `Decimal`.

`payment_date` remains legitimately nullable. Completed orders receive a
payment date from zero to three days after the order date (bounded by the fixed
data end date); Pending and Cancelled orders have no payment date. This is not
an intentional quality defect under the source contract.

## Fixed-row duplicate strategy

Duplicates reuse IDs within the required physical row counts; no rows are
appended.

- For customers, 10 target rows have their `customer_id` replaced with 10
  existing IDs. This means 10 rows are deliberately modified, 10 IDs form
  duplicate groups, and 20 physical rows participate in those groups.
- For orders, 20 target rows have their `order_id` replaced with 20 existing
  IDs. This means 20 rows are deliberately modified, 20 IDs form duplicate
  groups, and 40 physical rows participate in those groups.

Every duplicate group contains exactly two physical rows. This distinction is
important because a later uniqueness check using `duplicated(keep=False)` or a
window count will flag both the original row and the modified row.

## Intentional defects

The final customer data contains exactly:

- 50 rows with NULL `email`
- 10 rows modified to reuse existing `customer_id` values

The final order data contains exactly:

- 100 rows with NULL `customer_id`
- 200 rows with NULL `product_id`
- 50 rows with a non-null `customer_id` absent from customers
- 30 rows with a non-null `product_id` absent from products
- 20 rows modified to reuse existing `order_id` values

Customer NULL-email rows do not overlap duplicate-key members. All five order
issue groups are non-overlapping, including both physical members of each
duplicate-key group.

Products contain no intentionally seeded defects and retain 500 unique,
non-null product IDs.

## The approximate “~700 problematic rows” statement

The planning guide's approximate `~700 problematic rows` does not match the
explicit defect counts. The explicit counts describe 460 deliberately modified
rows or conditions:

```text
customers: 50 + 10
orders:    100 + 200 + 50 + 30 + 20
total:     460
```

With duplicate-group semantics, later uniqueness validation can flag 20
customer rows and 40 order rows. Because issue groups are kept separate, that
produces 490 physical rows participating in at least one specified issue:

```text
customers: 50 + 20 = 70
orders:    100 + 200 + 50 + 30 + 40 = 420
total:     490
```

No extra type or business-rule defects are invented to force the result toward
approximately 700. The explicit defect requirements take precedence.

## Validation performed by the generator

The script fails with a clear `ValueError` if any assertion is not satisfied.
Before writing CSV output, it validates:

- exact physical row counts
- exact required columns and order
- exact intentional NULL counts
- exact non-null invalid foreign-key counts
- no unintended foreign-key failures
- exact duplicate-row and duplicate-group conditions
- unique product IDs
- absence of unintended NULLs in required fields
- approved customer segments and order statuses
- non-negative monetary and inventory values
- positive order quantities
- exact `total_amount = quantity * unit_price` consistency
- non-overlap of intentional order issue groups

## Running the generator

From the repository root:

```text
python src/data_generation/generate_sample_data.py
```

The default output directory is the repository's `data/` directory. To write
to another location for a validation run:

```text
python src/data_generation/generate_sample_data.py --output-dir path/to/output
```

Required runtime libraries are pandas and Faker.
